# 生成：上下文是预算，不是仓库

晚上九点零几分，你为了「稳妥」，把 12 个候选块全塞进 prompt，心想材料给够总不会错。模型回得飞快，条理清晰，还贴心地把日期写上了——**写的是第 11 块里那份 2019 年试行版的日期**。你翻回前两块，2024 版的现行规定明明白白躺在那里，排第一，加粗都轮不到它。十二份材料一起递上去，模型像自助餐吃到第八道菜的人，记不清第一口是什么了。

**先给答案**：生成环节处理的不是「知识」，是**注意力预算**。检索给你的是证据，重排给你的是顺序，而这一环要决定：哪几块进 prompt、按什么位置摆、要求模型怎么用它、什么时候必须说「不知道」。把这些写成明确的约束，比换一个更贵的模型便宜得多。

## prompt 是三个槽位，不是一锅炖

一个可维护的 RAG prompt 至少分三块：**指令**（角色、只用给定材料、引用格式、不足就拒答）、**证据**（编号、来源、文本，最好带生效日期之类的元数据）、**问题**（放在最后，紧挨着模型的输出位置）。分开装的好处是能单独改、单独测，出问题时知道该改哪一段；一锅炖的后果是每次微调都像在整锅汤里找那粒盐。

证据块建议带编号与出处，例如 `[1] 报销制度 2024 版 §2.1：材料齐全后一般五个工作日到账`。这样引用不是让模型「凭记忆补一句」，而是**格式化的填空**：要求每个事实性句子后跟 `[n]`，评测时可以直接检查编号是否对应、内容是否被支持。[OpenAI Cookbook 里关于 RAG 与引用的示例](https://cookbook.openai.com/) 和 [LlamaIndex 的 response synthesizer 文档](https://docs.llamaindex.ai/en/stable/module_guides/querying/response_synthesizers/) 都采用这类结构化思路。

## 中间那块，模型看着看着就走神了

Liu 等人 2023 年的论文 [*Lost in the Middle*](https://arxiv.org/abs/2307.03172) 报告了一个很扎心的现象：在多文档问答里，把正确证据放在上下文开头或结尾时表现最好，放在中间时明显下降，整体呈 U 形（口径：论文在 GPT-3.5-Turbo 与 Claude-1.3 等模型上的多文档 QA 实验，具体降幅随模型与任务变化，别把它当成固定百分比）。这就是「上下文越长越好」这句话最贵的反例。

对应的工程动作很具体：重排之后别把 top-5 按分数 1→5 顺序直接拼进去，试试把第 1 名放最前、第 2 名放最后、其余依次向内，或者把最关键的证据在结尾再复述一次。另外给每块留一点「呼吸空间」，别压成没有空行的字符墙——模型读的是 token 序列，不是版式，但编号与分隔能帮它定位。顺便说一句，这也解释了为什么「多塞几块保底」经常适得其反：你保的是召回的底，赔的是注意力的钱。

## 引用和拒答是功能，不是提示词彩蛋

一个能被信任的 RAG 系统，必须能在**材料不够时闭嘴**。做法是把拒答写成一等公民：在指令里明确「若给定材料不足以回答，直接输出『资料中未找到依据』，不要用常识补全」，再配一个相关性阈值（比如重排最高分低于某值就不进生成）。没有这条，模型会非常体贴地用预训练知识替你把洞补上——补得语气越自然，越难被发现。

引用则要可核对：编号 → 块 → 原文 → 文档页码，这条链要能一路点回去。它同时是评测的抓手：**忠实度**（答案里的每个事实能否由给定证据推出）可以用 LLM-as-judge 或人工抽检来打分，[RAGAS 的 faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/) 就是这个思路。至于「模型胡编」这件事，请先检查它有没有被给到正确证据，再骂模型——这也是本站反复强调按环节归因的原因。

## 生成环节要单独验收：冻住检索，只改 prompt

验收生成时最容易犯的错，是边改 prompt 边改检索配置，最后不知道是谁起了作用。正确姿势是**冻结一批检索结果**（把 50 条问题的 top-5 证据保存成 JSON），然后只改 prompt、模型、摆放顺序，比较：答案正确率、忠实度、引用可核对率、以及「该拒答时有没有拒答」。这样测出来的差异才干净。等你把这一环稳住，再回去动前面的环节——评测章节会把这套单变量思路展开成完整流程。
